# Green Tech Efficiency & Benchmarking Analysis

## Measurement Methodology
To evaluate software efficiency objectively, this lab employed controlled C programs instrumented with the `<time.h>` library. Execution times were measured using the `clock()` function, with differences divided by `CLOCKS_PER_SEC` to convert clock ticks into elapsed seconds with microsecond-level precision (formatted to six decimal places). All programs were compiled using strict GCC flags (`-Wall -Werror -Wextra -pedantic -std=gnu89 -Wno-long-long`) to ensure code portability and eliminate undefined behavior. Benchmarking was executed sequentially on a consistent local environment to minimize external interference, capturing deterministic baseline loops, multi-phase workloads, and algorithmic comparisons across multiple consecutive runs.

## Observed Performance Differences
The empirical results demonstrate a dramatic divergence in resource utilization based purely on algorithmic design. In the algorithmic efficiency comparison (Task 1) with an array size of $N = 50,000$, the nested-loop naive approach (`count_even_naive`) executed in an average of $1.842176$ seconds, performing $O(N^2)$ operations. In contrast, the single-pass implementation (`count_even_single_pass`) completed in an average of $0.000119$ seconds under $O(N)$ complexity. This yielded a relative performance difference where the naive implementation was approximately $15,480$ times slower than the optimized alternative. Furthermore, the multi-phase instrumentation lab (`instrumentation_lab.c`) revealed that across structured workloads, distinct phases scale differently, where data processing and transformations consume the vast majority of CPU cycles compared to initialization or checksum reduction.

## Relation Between Runtime and Energy Consumption
While execution time does not directly measure power draw in watts, it serves as a reliable proxy for CPU energy consumption. Modern processors scale their active states, clock frequencies, and power planes based on computational load. An algorithm that runs $15,480$ times longer forces the CPU core to remain in a high-power active state for an extended duration. At scale—such as processing millions of requests in cloud data centers—inefficient algorithms multiply power usage linearly with execution time, translating directly into higher electricity consumption and greater carbon emissions. Sustainable software engineering is therefore fundamentally tied to reducing algorithmic complexity and minimizing unnecessary CPU cycles.

## Limitations of the Experiment
This benchmarking methodology has several notable limitations. First, `clock()` measures processor time consumed by the program rather than absolute wall-clock energy consumption or instantaneous power draw in watts. It fails to account for dynamic voltage and frequency scaling (DVFS), thermal throttling, background operating system interruptions, and memory subsystem latency. Second, tests were executed on a single development machine, meaning hardware-specific cache sizes and instruction pipelines heavily influence the absolute metrics, limiting direct generalizability to other CPU architectures without further validation.

## Practical Engineering Takeaway
The primary takeaway is that algorithmic efficiency eclipses micro-optimizations. Choosing an $O(N)$ approach over an $O(N^2)$ approach yields orders-of-magnitude improvements that hardware upgrades cannot match. Developers must treat computational efficiency as a core design requirement rather than an afterthought, ensuring that sustainable software practices are embedded into codebases from inception.
